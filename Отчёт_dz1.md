# TrainLog — учёт тренировок

## Доменная область

TrainLog — дневник силовых тренировок. Пользователь ведёт справочник упражнений,
записывает тренировки (дату, название, длительность, заметки) и фиксирует в каждой тренировке
выполненные подходы: какое упражнение, сколько повторений и с каким весом.
Каждый пользователь регистрируется по почте и паролю и видит только свои тренировки.

## Стек реализации

| Слой | Технологии |
|---|---|
| Backend | Java 25, Spring Boot 4.1 (Web MVC, Data JPA, Validation, Security, Session JDBC), Hibernate, Maven |
| База данных | PostgreSQL 18 |
| Миграции | Flyway 13 (отдельный контейнер) |
| Frontend | HTML, CSS, JavaScript без фреймворков, отдаётся nginx |
| Инфраструктура | Docker, Docker Compose |

Архитектура:

```
браузер ──► frontend (nginx) ──/api/*──► backend (Spring Boot) ──► db (PostgreSQL)
                                                                     ▲
                                              migrate (Flyway) ──────┘  (одноразовый запуск)
```

Nginx отдаёт статические файлы и проксирует запросы `/api/*` на бэкенд, поэтому фронтенд и API
работают на одном адресе и настраивать CORS не нужно.

Интерфейс — одностраничное приложение с навигацией по адресам: `#/workouts` (список тренировок
по месяцам), `#/workouts/{id}` (тренировка, её подходы и сводка), `#/exercises` (справочник с поиском
и фильтром по группам мышц). Создание и редактирование записей открывается в модальных окнах.

## Основные сущности

```
exercise 1 ──── * workout_set * ──── 1 workout
    *                                    *
    └──────────── 0..1 account 1 ────────┘
```

**Account (пользователь)**

| Поле | Тип | Ограничения |
|---|---|---|
| id | bigint | PK |
| email | varchar(100) | обязательное, уникальное, хранится в нижнем регистре |
| password_hash | varchar(100) | обязательное, BCrypt |

**Exercise (упражнение)** — элемент справочника. Упражнения без владельца общие: их видят все,
но менять нельзя.

| Поле | Тип | Ограничения |
|---|---|---|
| id | bigint | PK |
| account_id | bigint | FK → account, `on delete cascade`; пусто у общих упражнений |
| name | varchar(100) | обязательное, уникальное в пределах владельца без учёта регистра |
| muscle_group | varchar(20) | обязательное: CHEST, BACK, LEGS, SHOULDERS, ARMS, CORE, CARDIO |
| description | varchar(500) | |

**Workout (тренировка)**

| Поле | Тип | Ограничения |
|---|---|---|
| id | bigint | PK |
| account_id | bigint | FK → account, `on delete cascade` |
| performed_on | date | обязательное |
| title | varchar(100) | обязательное |
| notes | varchar(500) | |
| duration_minutes | integer | > 0 |

**WorkoutSet (подход)** — связывает тренировку и упражнение.

| Поле | Тип | Ограничения |
|---|---|---|
| id | bigint | PK |
| workout_id | bigint | FK → workout, `on delete cascade` |
| exercise_id | bigint | FK → exercise, `on delete restrict` |
| reps | integer | обязательное, > 0 |
| weight_kg | numeric(6,2) | ≥ 0 |

При удалении тренировки её подходы удаляются вместе с ней. Упражнение, которое используется хотя бы
в одном подходе, удалить нельзя: API вернёт `409 Conflict`.

## REST API

| Метод | Путь | Действие |
|---|---|---|
| POST | `/api/auth/register` | регистрация и вход |
| POST | `/api/auth/login` | вход |
| POST | `/api/auth/logout` | выход |
| GET | `/api/auth/me` | текущий пользователь |
| GET / POST | `/api/exercises` | список / создание упражнения |
| GET / PUT / DELETE | `/api/exercises/{id}` | чтение / изменение / удаление |
| GET / POST | `/api/workouts` | список / создание тренировки |
| GET / PUT / DELETE | `/api/workouts/{id}` | чтение / изменение / удаление |
| GET / POST | `/api/workouts/{id}/sets` | подходы тренировки / добавление подхода |
| PUT / DELETE | `/api/sets/{id}` | изменение / удаление подхода |

Вход выполняется по cookie-сессии. Все запросы, кроме регистрации и входа, доступны только
вошедшему пользователю; чужие тренировки, подходы и упражнения для него не существуют (404).

Ошибки возвращаются в формате RFC 9457 (Problem Details): 400 при ошибке валидации,
401 без входа или при неверном пароле, 404 если запись не найдена, 409 при нарушении целостности данных.

## Структура проекта

```
backend/            Spring Boot приложение
  src/main/java/ru/trainlog/
    auth/           пользователи, регистрация и вход, настройка Spring Security
    exercise/       сущность, репозиторий, сервис, контроллер, DTO упражнений
    workout/        тренировки и подходы
    common/         обработка ошибок
db/
  migration/        SQL-миграции Flyway
  Dockerfile        образ с миграциями
frontend/
  html/             index.html, app.js, style.css
  nginx.conf.template
docker-compose.yml
.env.example
```

## Запуск

```bash
cp .env.example .env      # при необходимости поменять пароль и порт
docker compose up --build
```

Приложение будет доступно по адресу http://localhost:8080.

## Соответствие методологии 12 факторов

### I. Кодовая база
Весь код хранится в одном git-репозитории: бэкенд, фронтенд, миграции и описание инфраструктуры.
Из одной кодовой базы можно развернуть любое число окружений (локальное, тестовое, продуктивное);
различаются они только конфигурацией.

### II. Зависимости
Зависимости бэкенда объявлены явно в `pom.xml`, их версии фиксирует Spring Boot parent.
Приложение не рассчитывает на системные библиотеки: всё окружение описано в Dockerfile
(базовые образы `eclipse-temurin:25.0.4.1_1-jre`, `nginx:1.30.5-alpine`,
`flyway/flyway:13.8.1-alpine`, `postgres:18.4-alpine`). Теги образов закреплены на точных версиях.
Для сборки не нужны локальные JDK и Maven, образ собирается внутри Docker.

### III. Конфигурация
Всё, что меняется между окружениями, передаётся через переменные окружения:
`DB_URL`, `DB_USER`, `DB_PASSWORD`, `PORT` для бэкенда, `BACKEND_URL` и `PORT` для nginx,
`FLYWAY_*` для миграций. В `application.yml` стоят только плейсхолдеры `${...}`.
Секреты в репозиторий не попадают: `.env` добавлен в `.gitignore`, в репозитории лежит только
шаблон `.env.example`. Если `DB_URL` не задан, приложение не стартует. Так ошибка конфигурации
видна сразу, а не маскируется значением по умолчанию.

### IV. Сторонние службы
PostgreSQL — подключаемый ресурс, который бэкенд находит только по URL и учётным данным.
Чтобы заменить локальный контейнер на управляемую БД в облаке, достаточно поменять `DB_URL`,
код менять не нужно. Бэкенд для фронтенда тоже внешний ресурс, адрес задаётся через `BACKEND_URL`.

### V. Сборка, релиз, выполнение
- **Сборка:** многоэтапный `backend/Dockerfile` компилирует код и собирает jar,
  финальный образ содержит только JRE и готовый jar.
- **Релиз:** собранный образ вместе с конфигурацией из `.env` / переменных окружения.
  Каждый релиз имеет идентификатор: образы помечаются тегом из `APP_VERSION`
  (`trainlog-backend:1.0.0` и т.д.).
- **Выполнение:** `docker compose up` запускает контейнеры из готовых образов.

В работающем контейнере код не меняется. Любое изменение требует пересборки образа с новой версией.
Старые образы остаются, поэтому откат делается без сборки:
`APP_VERSION=1.0.0 docker compose up -d --no-build`.

### VI. Процессы
Бэкенд не хранит состояние: нет локальных файлов и кешей в памяти между запросами, HTTP-сессии
лежат в PostgreSQL (Spring Session JDBC). Все данные хранятся в PostgreSQL. Поэтому любой запрос может обработать любой экземпляр
приложения, а экземпляр можно перезапустить без потери данных.

### VII. Привязка портов
Бэкенд — самодостаточный сервис со встроенным Tomcat. Он сам слушает порт из переменной `PORT`
и не требует внешнего сервера приложений. Фронтенд так же сам слушает свой порт через nginx.
Наружу публикуется только порт фронтенда (`APP_PORT`).

### VIII. Параллелизм
Благодаря VI фактору приложение масштабируется горизонтально запуском дополнительных процессов:

```bash
docker compose up -d --scale backend=3
```

У бэкенда нет опубликованных портов, поэтому реплики не конфликтуют. Nginx обращается к ним
по DNS-имени `backend`, которое Docker резолвит во все реплики. Имя резолвится динамически
(`resolver 127.0.0.11 valid=10s` и `proxy_pass` через переменную), поэтому новые реплики
подхватываются без перезапуска nginx.

### IX. Утилизируемость
- Быстрый старт: около 5 секунд, миграции выполняются заранее в отдельном контейнере.
- Корректное завершение: включён `server.shutdown: graceful`. По `SIGTERM` (`docker stop`)
  приложение перестаёт принимать новые запросы, дожидается завершения текущих и закрывает
  пул соединений. На это Spring даёт до 30 секунд, поэтому в compose задан
  `stop_grace_period: 35s` (по умолчанию Docker ждёт 10 секунд и убивает процесс).
- Упавшие контейнеры поднимаются сами: `restart: unless-stopped`.
- Процессы можно убивать и перезапускать в любой момент, данные при этом не теряются.

### X. Паритет разработки и эксплуатации
Во всех окружениях используются одни и те же образы и одна и та же СУБД — PostgreSQL 18.
Встраиваемые БД (H2) для разработки не используются. Локальное окружение поднимается той же
командой `docker compose up`, что минимизирует разрыв между разработкой и эксплуатацией.

### XI. Журналирование
Приложение пишет логи только в stdout/stderr (стандартный консольный вывод Spring Boot)
и не управляет файлами логов. Сбором и хранением занимается окружение:
`docker compose logs -f backend`. В продуктивной среде поток можно направить в любую
систему агрегации логов без изменения кода.

### XII. Задачи администрирования
Миграции схемы БД — разовая административная задача. Она оформлена отдельным процессом
(сервис `migrate` на Flyway), который использует тот же репозиторий и ту же конфигурацию,
что и приложение. Бэкенд стартует только после успешного завершения миграций
(`service_completed_successfully`), а Hibernate лишь проверяет соответствие схемы
(`ddl-auto: validate`) и ничего в ней не меняет. Миграции можно запустить и вручную:

```bash
docker compose run --rm migrate
docker compose run --rm migrate info
```
